## 챗봇 처리 흐름

챗봇은 로그인 없이 `질문 → RoBERTa(CPU) → 규정·회사 정보·사내 생활 DB 검색 → LLM 근거 답변 → 서버 검증`으로 동작해요. 서버의 Ollama 규정 모델 설정을 사용하며 개인 AI 모드·가데이터·추론 설정은 읽지 않아요. 다른 에이전트의 계정별 설정과 지원 조건 확인은 유지해요.

### 익명 자료 기반 챗봇 (#68)

`POST /assistant/ask`는 로그인 세션·회원 프로필·직급·부서·개인 로드맵을 조회하지 않아요. 모델의 `user` 입력은 빈 객체이며, 사용자가 질문·앞 대화에 직접 적은 조건만 참고해요. 기존 계정 정보가 섞일 수 있는 브라우저 대화는 새 저장 키로 분리하고 자동으로 이어 보내지 않아요.

규정 검색은 계정의 직원 구분 대신 등록된 전체 검색 대상에서 수행하고 각 조항의 `appliesTo`를 모델에 전달해요. 국외근무 자료는 기존처럼 관련 질문일 때만 포함해요. 질문에 대상이 없으면 특정 직급을 추정하지 않으며 서로 다른 대상의 기준을 섞지 않도록 지시해요. 기존 직원 구분 검색의 기본값은 유지하고 챗봇에서만 `all_groups=True`를 사용해요.

작업 상태·결과는 기존 `app_ext.jobs`에 직원 ID 없이 저장하며, `GET /assistant/jobs/{id}`·`POST /assistant/jobs/{id}/cancel`은 익명 `assistant` 작업만 다뤄요. 다른 종류·계정 소유 작업은 404예요. UUID 작업 ID는 결과 조회에 필요한 값이며 UI 요청은 로그인 쿠키를 보내지 않아요. 로그인 화면에서도 챗봇을 열 수 있어요. 호출 메타데이터는 기존 기록 기능에 익명으로 남아요.

관련 이슈: [#68](https://github.com/20260528-skn-family-ai-33/SKN33-Final-2Team/issues/68). 사용자 요청에 따라 로그인 분리와 라벨 병렬 표시까지 포함해요. 담당자·검토자·예상 기간·목표일, Notion/WBS는 미정이며 PR #65의 기존 이어 묻기 수정에 이어 작업해요.

| 학습 라벨 | 처리 |
| --- | --- |
| 범위 밖 | 규정 검색과 LLM 호출 없이 기존 범위 밖 안내 |
| 사내 규정 | 등록된 규정 검색·원문의 적용 대상 전달·근거/숫자 검사·LLM 답변 |
| 사내 생활안내 | DB `knowledge`의 생활 범주 검색·근거/숫자 검사·LLM 답변. 가상 여부와 자료 제약을 출처에 유지 |
| 수자원공사 정보 | DB `knowledge`의 실제 회사 자료를 검색해 답변·출처를 제공. 근거가 부족하면 확인 불가 안내 |

회사 정보는 `knowledge.documents.category=수자원공사 정보`인 실제 자료만 검색해요. 기존 연결 확인 기록은 회사 문서 3종·137개 청크, 가상 생활안내 305개 청크예요. 이번 작업에서 실제 DB 건수를 다시 조회하지 않았어요. 생활 자료는 회사 검색에서 제외하고 생활 범주에서 별도로 검색해요. 후속 질문은 앞 대화의 주제와 요약을 분류·검색에 사용하고, `meta.classification.usedHistory`로 분류기의 요약 사용 여부를 알려 줘요. 실제 분류 모델의 정확도·검색 품질은 별도 평가가 필요해요.

## 답변 상태와 오류 (2026-11-03 사용자 요청 반영)

분류는 RoBERTa가 한 번 결정합니다. LLM에는 질문 유형을 다시 분류시키거나 화면의 `answer.kind`를 만들게 하지 않습니다. 규정과 회사 자료는 기존 검색으로 고르고, LLM은 전달된 자료에서 질문에 필요한 근거를 골라 답변합니다. RoBERTa 가중치·학습은 변경하지 않습니다. 오분류 자체를 해결한 작업은 아닙니다.

사용자 요청에 따라 실제 모델 모드의 되묻기(`clarify`·선택지)는 삭제했습니다. 2026-10-26의 되묻기 확대 기록은 과거 동작이며 현재 요구사항이 아닙니다. 가데이터의 고정 되묻기와 이전 대화의 되묻기 카드는 호환을 위해 유지합니다.

| `evidenceStatus` | 규정 표시 | 회사 표시 | 의미 |
| --- | --- | --- | --- |
| `found` | 규정 근거 확인 | 회사 근거 확인 | 질문 전체를 자료로 확인하여 인용과 함께 답변 |
| `partial` | 규정 근거 일부 확인 | 회사 근거 일부 확인 | 확인한 부분만 답하고 부족한 부분 설명 |
| `not_found` | 규정 근거 확인 불가 | 회사 근거 확인 불가 | 이번 검색 자료로 질문에 답할 근거가 없음 |
| `refused` | 규정 답변 불가 | 회사 답변 불가 | 비공개 개인정보·비밀정보 공개·권한 우회처럼 제공하면 안 되는 요청 거절 |

사내 생활도 `found`·`partial`·`not_found`·`refused`를 구분합니다. 규정·회사·생활 DB 답변에는 ML 분류 옆에 `근거 확인`·`근거 일부 확인`·`근거 확인 불가`를 나란히 표시합니다. 제공 금지 거절은 `답변 불가`, ML 범위 밖은 `범위 밖`, 연결·검증 실패는 `오류`라는 단일 결과 라벨을 표시합니다. LLM의 네 상태와 시스템 오류를 합쳐 UI 결과를 구분하며, 오류를 LLM 출력 라벨로 요청하지 않습니다. 예전 메뉴형 답변 표시는 이전 기록 호환용으로 남습니다.

생활 검색은 `knowledge.documents.category=사내 생활안내`로 한정하고 DB의 원문·문서명·위치·자료 시점·가상 여부·제약을 전달합니다. 실제 인용한 자료만 `knowledgeSources`에 담고 원문 발췌(`excerpt`)와 가상 표시를 화면의 ‘사내 생활 근거 보기’에 제공합니다. DB 자료가 없으면 고정 메뉴로 대체하지 않으며, 가상 식단·시간표·연락처를 실제 운영 정보로 단정하지 않도록 지시합니다. 사실성·검색 품질은 별도 평가가 필요합니다.

연결·시간 초과·JSON 파싱·출처/숫자 검증 실패는 기존 작업 실패 응답을 유지하며 화면에 **오류**로 표시합니다. 검색 실패나 제공 금지 거절로 숨기지 않습니다. 잘못된 인용 ID를 버리고 `근거 확인 불가`로 처리하던 규정 경로도 오류로 구분합니다. LLM의 거절 응답에 민감한 원문이 섞여도 사용자에게는 서버의 고정 거절 안내만 제공합니다.

검색 결과가 비어도 LLM에 빈 근거 목록을 전달해 제공 금지 요청인지 구분합니다. 빈 목록으로 근거 답변을 생성하면 오류이며, 허용된 요청의 자료 부족만 `not_found`로 반환합니다. 따라서 범위 밖을 제외한 규정·회사 질문은 검색 결과가 없을 때도 답변 모델을 1회 호출할 수 있습니다.

모델 출력은 세 필드 `{"status":"found|partial|not_found|refused","summary":"...","sourceIds":["S001"]}`로 통일합니다. 서버가 `S001` 같은 짧은 별칭을 실제 검색 ID로 복원하며, 없는 ID·빈 근거 답변·상태/인용 불일치를 거절합니다. `found`·`partial`은 반드시 유효한 인용과 비어 있지 않은 요약이 필요합니다. 인용·숫자 확인은 근거 존재 검사이며 문장 전체의 의미적 사실성을 보증하지 않습니다.

실제 모델의 규정 답변은 ‘내 상황에 적용’(`apply`)·‘추가로 확인할 것’(`more`)·‘등록되지 않은 기준’(`missing`)을 별도 생성 항목으로 요청하지 않습니다. 확인된 내용·적용 조건·확인하지 못한 부분은 `summary`에 담습니다. 특히 다른 별표·기준을 참조하지만 제공 자료에 없으면 `partial`과 요약으로 부족한 부분을 알립니다. 기존 API 필드와 화면 표시는 가데이터·이전 대화 호환을 위해 남아 있으며, 필드가 남아 있다는 사실이 현재 모델의 별도 생성 요구를 뜻하지 않습니다.

독립 질문에는 과거 질문·근거를 섞지 않습니다. 이어 묻기는 기존 짧은 표현에 더해 ‘그 규정에서 …’, ‘앞에서 설명한 내용을 내 상황에 적용하면 …’, ‘온라인 교육도 교육비 지원을 받을 수 있나요?’처럼 앞 내용을 가리키거나 조건을 보태는 표현을 길이와 관계없이 연결합니다. ‘다른 질문’, ‘새 주제’처럼 주제 변경을 밝히거나 범위 밖 키워드가 있으면 이전 맥락을 분리합니다. 이는 규칙 기반 연결이며 모든 자연어 표현의 의미를 판별하는 모델은 아닙니다.

규정 답변에서 규정 이름 없이 조항 번호를 물으면 이 판별과 별도로 직전 답변의 첫 근거가 속한 규정을 참조합니다. 예를 들어 ‘인재개발규정 제7조 알려줘’ 다음 ‘그 규정 제9조 내용을 알려줘’는 제9조를 자료의 맨 앞과 `requested`에 넣고 이전 대화 요약도 전달합니다. 미등록 조항이면 찾지 못한 규정명·조 번호를 안내하며 다른 검색 조항으로 대신 답하지 않습니다. 명시한 규정 이름은 직전 규정보다 우선하며, 직전 근거가 없거나 삭제됐으면 규정을 추측하지 않습니다. `meta.classification.usedHistory`는 분류기가 앞 대화 요약을 사용했는지만 뜻하므로, 조항 참조 단계에서만 이전 규정을 사용하면 이 값은 거짓일 수 있습니다.

이전 대화는 이어진 구간의 첫 질문(주제)·최근 두 질문과, 이미 생성된 답변의 `summary`를 중복 없이 묶은 두 메시지로 압축합니다. 중간 답변의 적용 조건이 사라지지 않게 그 구간의 답변 요약은 누적하며, 전체 대화 원문을 반복해서 넘기거나 요약용 LLM을 추가 호출하지 않습니다. 화면에 본문 요약을 저장하지 않는 생활 안내는 검증된 메뉴 위치·안내 범위로 요약을 구성합니다. 분류 입력은 현재 질문을 먼저 두고 첫 주제와 최근 답변 요약을 각각 최대 60자 붙입니다(분류기 입력 한도 128토큰). 검색은 현재 질문과 압축한 대화를 사용하고, 답변 모델도 같은 대화 요약을 참고합니다. 긴 현재 질문에서는 분류기의 입력 한도로 요약 일부가 잘릴 수 있습니다.

`kind`·`level` 같은 이전 응답 구조와 `basis`의 실제 출처 ID는 모델 대화에 넘기지 않습니다. 저장된 대화·가데이터의 API 형식은 유지하며, 서버는 조항을 찾을 때만 이전 `basis`를 참조합니다. 이번 답변의 출처는 이번에 전달한 자료의 `S001` 같은 별칭으로 검증합니다. 시스템 프롬프트에도 요약의 주제·조건으로 후속 질문을 해석하되, 그 요약 자체를 사실 근거로 삼거나 앞 답변만 반복하지 않도록 명시합니다.

Ollama 챗봇 답변에는 `temperature=0`을 보내 생성 변동을 줄이며, 동일 결과를 절대 보장하거나 다른 에이전트의 생성 설정을 바꾸지는 않습니다.

챗봇 파인튜닝 모델(`growpath-regulation-4b` · `qwen35-4b-diagnosis-agent`) 호출에는 `options.num_gpu=-1`을 보내 Ollama 서버가 GPU·VRAM에 맞춰 자동 배치합니다. 지원 GPU가 없으면 CPU를 사용합니다. 진단·로드맵 모델의 장치 옵션과 RoBERTa CPU 분류 설정은 바꾸지 않습니다.

Docker는 `backend/models`를 `/srv/growpath/models`에 읽기 전용으로 붙여요. 모델 파일은 이미지 빌드에 포함되지 않아요. 호스트의 모델 위치는 항상 `backend/models/`이고 컨테이너에서는 같은 파일을 `/srv/growpath/models/`에서 읽어요. 최상단 requirements를 사용하도록 Docker 빌드 컨텍스트도 저장소 맨 위로 두고, `backend/Dockerfile.dockerignore`로 필요한 코드·의존성 파일만 허용해요.
