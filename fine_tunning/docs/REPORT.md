LoRA 병합은 두 저랭크 행렬의 곱을 스케일한 **변경분을 기본 가중치에 더하는 과정**. 기본 가중치 자체와 어댑터를 단순히 곱하는 방식과 구분. 병합 후 별도 어댑터 경로 없이 전체 모델 로드가 가능한 배포 형태이며, 모델 파라미터 수나 BF16 저장 용량이4B처럼 줄어드는 경량화는 아님.

| 승인·효력일 제한 | 기본 검색에서 active·approved·available·유효일 조건 | 폐지·미승인·이용 불가 규정을 현행 답변 근거로 쓰지 않도록 구분 | 검토 포함 옵션 결과는 requires_review와 함께 표시 |
| top5·0.25 | 코사인 유사도 내림차순, 기본5개·임계0.25 | 반환량과 최소 유사도 제한을 코드 기본값으로 제공 | 0.25가 정답 확률25%는 아님. 최적 임계값 실험 미확인 |

규정 벡터 PK는 `(rag_chunk_id, embedding_model)`이다. 같은 청크의 모델별 벡터를 구분하며, 재임베딩 시 대응 행을 갱신한다. 확인한 DDL의 `embedding_model` B-tree는 모델 필터용이고 HNSW·IVFFlat 같은 근사 최근접 벡터 인덱스와 다르다.

### 학습 자료: 레코드 단위 임베딩

```text
스킬·강좌·도서·자격·직무·전공 레코드
  → 허용 필드와 연결 스킬 추출 → 정렬 JSON
  → 긴 필드 축약·8,000바이트 검사
  → 원본 SHA·모델·차원과 벡터1개 저장
  → 현재 적격 자료·현재 SHA 기준 코사인 유사도
```

| 처리 선택 | 이유·효과 | 실제 한계 |
|---|---|---|
| 자료1개당 벡터1개 | 강좌·도서 등 추천 가능한 실제 자료ID와 검색 결과의 직접 대응 | 장문 자료를 여러 의미 단위로 쪼개는 문서 검색 방식과 다름 |
| 허용 필드·연결 스킬 포함 | 제목만이 아니라 설명·교육과정·관련 역량의 일관된 표현 | 포함하지 않은 원문 전체까지 검색된다고 주장하지 않음 |
| 정렬 JSON 직렬화 | 필드 순서 차이로 입력·해시가 불필요하게 달라지는 현상 축소 | 값 변경은 새 입력·재임베딩 대상 |
| 설명 등 긴 필드 순차 축약 | 설정된8,000 UTF-8바이트 입력 예산 안에서 자료 단위 유지 | 각 대상 문자열을 최소160자까지 보존해도 초과하면 API 호출 전 오류 |
| 공식 근거·이용 가능성 확인 | 종료 강좌·무효 자료·누락 메타데이터 등 부적격 후보 배제 | 일부 근거는 최대30일 유효기간. 자료 유형별 조건 상이 |
| 현재 SHA로 결과 제한 | 수정 전 자료 내용으로 만든 벡터가 재사용되는 문제 차단 | 누락·오래된 벡터는 오류 처리. 조용한 성공으로 바꾸지 않음 |

자료 벡터 PK는 `(resource_type, resource_id, embedding_model)`이다. 자료 종류별 FK가 정확히1개 연결되도록 제약한다. `similarities`는 요청 자료 키에 대한 정확 코사인 유사도를 반환하며 함수 자체에 고정top-k·임계값은 없다. 최종 추천의 필터·순위와 구분한다.

### 8,000바이트·문자·토큰의 구분

8,000은 현재 코드의 **UTF-8바이트 제한**이다. 모델 API의 공식 토큰 최대치와 같은 단위가 아니다. 한글은 일반적으로 글자당 여러 UTF-8바이트를 사용하므로 ‘8,000자’ 또는 ‘8,000토큰’으로 표기하지 않는다. 현재 전달 규정 파일1,552개는 경로+본문의8,000바이트 초과가0개이며, token_count는 전부NULL이다.

규정은 API 입력의 앞부분만 사용하지만 원문·원본 SHA는 전체를 보존한다. 따라서 긴 규정이 생기면 전체 SHA가 같더라도 임베딩에 후반부가 포함됐다고 볼 수 없다. 학습 자료는 축약 후에도 초과하면 오류를 내므로 두 경로를 같은 잘림 정책으로 설명하지 않는다.

### RAG 청크와 파인튜닝 샘플의 구분

규정·학습 자료 청크는 검색에 사용하는 외부 근거다. 파인튜닝1,500/3,000건은 messages 형식의 학습 사례이고, max_length7168/10240은 모델 학습 입력의 토큰 길이 설정이다. **청크1,552개·8,000바이트·학습3,000건·max_length10240은 서로 다른 지표**다. 현재 청크 상태와 벡터 적재·승인 여부는 DB 실조회 없이 확정하지 않는다.

## DB와 백엔드 준비

1. Docker Desktop의 Linux 엔진 실행 후 `docker version`에서 Server 응답 확인. 현재는 엔진 파이프가 없다는 오류 확인.
2. 담당자에게 **권한 있는 팀 DB 덤프**를 받아 `team_db/growpath_latest.dump`에 배치. 직원·인증 해시가 포함될 수 있어 Git·일반 전달 ZIP 제외. 다른 프로젝트의 덤프를 자동 복사하지 않음.
3. 필요한 규정 원문은 `team_db/README.md`, 복원·무결성 계약은 `database/RESTORE.md` 확인. `.env`의 `TEAM_DB_FILE`과 파일명 일치 확인.
4. `.env`의 로컬 DB 비밀번호·포트·이름 확인. 시연 계정 비밀번호·API 키는 담당자에게 받은 실제 값만 입력. 공란은 가짜 값으로 보충하지 않음.
5. 준비 후 실행:

```powershell
# Docker 전체 실행은 빈 DB 복원과 backend-setup에 쓰기가 포함됨.
# 이미 운영 중인 DB를 대상으로 무조건 실행하지 말고 .env의 프로젝트명·포트·볼륨 확인.
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

로컬 Python 백엔드만 실행하는 경우 먼저 DB·보조 스키마·규정 준비가 필요. 다음 래퍼는 연결 실패 시 종료하며 DB를 자동 초기화하지 않음.

```powershell
./scripts/start-backend-local.ps1
# API 문서 http://localhost:8815/api/docs
```

현재 DB 덤프·Docker 엔진이 준비되지 않아 위 실서비스 기동과 사용자 로그인은 수행하지 않음. 앱 import·OpenAPI 생성은 DB 미접속으로 따로 검증.

## V18 연결에서 확인된 계약 차이

최종 모델은 `Ssum-mer/qwen3.8-27b-growpath`, 27B·2에폭·BF16 병합 모델. HF revision `66d1af509ab0681f3b9365227e5c794c65801fbf`. 모델을 폴더에 넣는 것만으로 현재 백엔드에 연결되지는 않음.

| 구분 | 현재 팀 백엔드 | 파인튜닝 런타임 | 필요한 대응 |
|---|---|---|---|
| 호출 프로토콜 | Ollama `/api/chat` 또는 OpenAI `/chat/completions` | HF 전체 모델 가중치 | 실제 서빙 서버와 모델 별칭 검증 |
| 입력 | `handoff`, `catalog`, `skillTags`, `current` | `user_context`, `retrieved_context`, `task_data` | 명시적 입력 변환 |
| 생성 출력 | `acts[{stage,title,res,hours,how,skills}]` | `milestones`, `roadmap_flow`, 근거 ID 배열 | 활동별 출력 변환·필드 검증 |
| 수정 출력 | 기존 `key`·`done`과 활동 기록 유지 | JSON preserve_paths·완료 기록 유지 | 기존 활동 ID와 원문 필드의 보존 매핑 |
| 자료 ID | catalog의 단일 `res` 문자열 | course_id / isbn / cert_id | 실제 catalog ID 대응표 필요, 문자열 접두어 추정 금지 |
| 자료 시간 | `finish_option`이 DB 자료 시간으로 다시 설정 | milestone별 hours | 변환 후 총시간·비용 재검증 |
| 관점 | A1 비용 / A2 시간 / A3 업무 | 프리 / 크래쉬 / 챌린지 제안 | 표시명과 실행 ID 구분 |

현재 `backend/app/agents/roadmap.py`의 `finish_option`은 `acts`를 읽으므로 V18의 `milestones`를 그대로 넣으면 활동 없음 오류. 단순 모델명 변경이나 필드 이름 치환만으로 연결 완료 처리하지 않음. 백엔드는 참고용 사본이므로 기존 기능·공통 계약을 임의로 수정하지 않았으며, 담당자 검토용 연결 조건을 이 문서에 정리.

## 서빙 준비 절차

### 현재 프로토콜을 유지하는 Ollama 경로

1. 담당 GPU 호스트에서 설치 Ollama 버전이 게시 config의 `Qwen3_5ForConditionalGeneration`과 tokenizer·chat template를 지원하는지 확인.
2. 고정 HF revision의 전체 모델을 별도 경로에 확보하고 manifest·샤드 수 확인. 이번 작업에서54.71GB 가중치를 다운로드하지 않음.
3. [공식 Safetensors import 안내](https://docs.ollama.com/import)에 따라 모델 디렉터리를 FROM으로 지정한 Modelfile과 `ollama create growpath-v18 -f Modelfile` 사용. 지원되지 않는 아키텍처면 임의 config 수정·다른 모델 대체 없이 중단.
4. import와 최소 출력 검증 후 실제 별칭을 `.env`의 `OLLAMA_MODEL_ROADMAP`에 기록. `OLLAMA_MODEL`은 검증된 일반 역할 모델명, 주소·키는 실제 서빙 값. 아직 준비되지 않은 별칭을 설정하지 않음.
5. 모델이 호출되더라도 위 입출력 변환·시간/비용·수정 보존 검증이 별도로 필요. 규정 검색 임베딩은 기존 OpenAI1536차원 계약 유지.

### HF 그대로 사용하는 OpenAI 호환 서빙 경로

[vLLM 지원 모델 목록](https://docs.vllm.ai/en/latest/models/supported_models/)과 [Qwen 계열 안내](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3.5.html)를 기준으로 해당 아키텍처 지원 버전을 별도 Linux GPU 환경에서 고정. Windows 앱용 Conda에 학습·서빙 CUDA 패키지를 섞지 않음. 예시 명령은 실제 GPU 호스트·권한·메모리 확인 후 담당자가 실행할 인터페이스 참고:

```bash
vllm serve Ssum-mer/qwen3.8-27b-growpath   --revision 66d1af509ab0681f3b9365227e5c794c65801fbf   --served-model-name growpath-v18 --dtype bfloat16   --max-model-len 7168 --host 127.0.0.1 --port 8000
```

현재 백엔드의 `OPENAI_BASE_URL`은 채팅과 임베딩에 **공유**됨. 이를 생성 전용 vLLM 주소로 바꾸면 규정 임베딩 호출까지 같은 서버로 가므로, 채팅/임베딩 endpoint 분리 없이 단순 설정 변경하지 않음. 입출력 변환과 endpoint 분리에는 백엔드 담당자 검토·이슈/PR가 필요하며 이번 로컬 환경 작업에서 등록·통합 완료로 표시하지 않음.

이전 종료 Pod 재접속·재시작·GPU 구매·유료 API·새 추론 없음. 서빙 절차를 적었다는 사실과 실제 V18 실시간 서비스 연결 완료를 구분.
